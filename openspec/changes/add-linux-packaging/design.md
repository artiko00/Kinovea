# Design

## Context

See proposal.md. Current state: `Installer/kinovea.nsi` bundles `Kinovea/bin/x64/Release`, writes registry keys and shortcuts, and `makeportable.py` zips the same tree; `build.yml` carries `VERSION: 2026.1.0`, duplicated in `kinovea.nsi` and `AssemblyInfo.cs`. `Kinovea.Updater` reads `https://www.kinovea.org/setup/update.xml` and shows `UpdateDialog2` with a download button. The Rust workspace version is `0.1.0`; the binary already prints `kinovea <version>` from `CARGO_PKG_VERSION`. Icon source: `Kinovea/Resources/kinovea-256x256.ico`. Assets the binary needs at run time: locales (embedded by change 18), `Tools/DrawingTools` XML and `Tools/XML/Schema` (embedded or copied by changes 05 and 14).

## Goals / Non-Goals

**Goals:**
- Installable artifacts for the two mainstream Linux distribution channels with the same binary.
- No manual version editing anywhere but `rust/Cargo.toml`.
- Release process runnable without the Windows host.

**Non-Goals:**
- Replacing `build.yml` now; it keeps producing Windows artifacts until `remove-dotnet-solution`.
- Flathub submission.

## Decisions

### D1. AppImage via `linuxdeploy` + `appimagetool`, Flatpak via `flatpak-builder` (requires approval)
AppImage gives a single file for users who do not run Flatpak; Flatpak gives sandboxing and the launcher integration most desktops expect. Both consume the same `packaging/share/` assets. Tool versions are pinned by URL + sha256 in `packaging/appimage/tools.lock`. Alternative `cargo-dist`: good for CLI tools, weak on desktop integration and Flatpak; rejected.

### D2. Flatpak manifest
`packaging/flatpak/org.kinovea.Kinovea.yml`: runtime `org.freedesktop.Platform//24.08`, sdk extension `org.freedesktop.Sdk.Extension.rust-stable` for offline builds with `cargo-sources.json` generated by `flatpak-cargo-generator`. Finish-args: `--socket=wayland --socket=fallback-x11 --device=dri --device=all` (cameras), `--socket=pulseaudio` (audio trigger), `--share=network`, `--filesystem=host:ro` plus `xdg-videos` read-write (recordings). Application id `org.kinovea.Kinovea` follows the upstream domain; if upstream objects, switch to `io.github.artiko00.Kinovea` (open question below does not block tasks).

### D3. Version single source
`workspace.package.version` in `rust/Cargo.toml` is read by: the binary (`env!("CARGO_PKG_VERSION")`), `packaging/version.sh` (uses `cargo metadata`) for artifact names and `metainfo.xml` `<release version>` injection, and `release.yml` which compares it with the tag and fails on mismatch. `rust.yml` needs no version. The first Rust release bumps the version to the Kinovea scheme (`2026.x.y`) so the update check compares like with like.

### D4. Release workflow
`.github/workflows/release.yml` on `push: tags: v*`: checkout, pinned toolchain, `make package` (AppImage), `flatpak-builder --repo` + `flatpak build-bundle`, smoke steps (`./Kinovea-*.AppImage --version`, `desktop-file-validate`, `appstreamcli validate --no-net`, open `Tools/XML/Schema/samples/simple.kva` with `--check-open` which exits after loading without a window using the headless renderer from change 06), then `softprops/action-gh-release` with `SHA256SUMS`. Workflow files require approval; the task says so.

### D5. Update notice instead of updater
`rust/kinovea/src/update.rs`: `ureq` GET `https://api.github.com/repos/artiko00/Kinovea/releases/latest` with a 3 s timeout on a background thread, compare `tag_name` by numeric components, post a message to the UI channel. Help > Check for updates reuses the same function synchronously with a spinner. No download. Rationale: AppImage users update by replacing the file, Flatpak users through their package manager; a self-updater would duplicate both.

### D6. Desktop assets
`packaging/share/applications/org.kinovea.Kinovea.desktop` (`MimeType=application/x-kinovea-kva;video/*;`, `Exec=kinovea %F`), `mime/packages/org.kinovea.Kinovea.xml` (glob `*.kva`, root element `KinoveaVideoAnalysis`), icons rendered from the `.ico` frames with `icotool` at build time plus a traced SVG committed once, `metainfo/org.kinovea.Kinovea.metainfo.xml` with screenshots from the upstream site.

## Legacy superseded

`Installer/kinovea.nsi`, `Installer/makeinstaller.py`, `Installer/makeportable.py`, `Installer/prepare-signing.ps1`, `restore-signed.ps1`, `verify-signature.ps1`, `Installer/OtherFiles/*`, `Installer/graphics/*`, `Kinovea.Updater/*` (Updater.cs, UpdateDialog2, Languages), the `VERSION` env of `build.yml`, `Kinovea/Properties/AssemblyInfo.cs` version attributes. UI text goes through Fluent (`add-i18n-fluent`), not `.resx`.

## Risks / Trade-offs

- [glibc of the build runner too new for older distributions] → build the AppImage inside a `ubuntu:22.04` container step; smoke-test on that image.
- [Wayland/X11 differences for egui/wgpu inside Flatpak] → test both sockets in CI with `xvfb-run` for X11 and `weston --headless` for Wayland; the `--check-open` smoke runs headless anyway.
- [GitHub API rate limit for the update check] → one unauthenticated call per start is within limits; cache the last answer for 24 h in the preferences directory.
- [Application id dispute] → id lives in one variable in `packaging/Makefile`; renaming is a one-line change plus file renames.

## Migration Plan

1. Assets and version script. 2. AppImage with `make package`, smoke checks. 3. Flatpak manifest. 4. `release.yml` after approval; tag a pre-release to test. 5. Update notice. Rollback: delete `packaging/` and the workflow; nothing else depends on them.

## Open Questions

- Whether upstream agrees to `org.kinovea.Kinovea`; fall back to `io.github.artiko00.Kinovea` without changing specs or tasks.
