# Design

## Context

See proposal.md for motivation. Constraints that shape this design:

- The C# solution compiles only with MSBuild and the C++/CLI toolset on Windows. The developer works on Linux and has SSH access to a Windows 11 Pro host on the LAN (`windows`, 20 threads, 32 GB RAM) that has Git, winget and Docker Desktop with a Linux backend, but no MSBuild, Visual Studio or dotnet SDK.
- The repository root is already a .NET solution with 22 projects, an NSIS installer and two GitHub workflows. The Rust code must coexist with it until the final `remove-dotnet-solution` change.
- Later changes depend on reference outputs of the original implementation (KVA files, kinematics series, exports) to practice TDD. Those outputs must be reproducible and reviewable in pull requests.
- The end goal includes a headless MCP server, so the workspace layout must keep domain crates free of UI dependencies from the start.

## Goals / Non-Goals

**Goals:**
- One `cargo` command verifies the whole Rust side on Linux; CI enforces it.
- Fixtures are generated by the original C# code, deterministically, and committed; tests never reach the Windows host.
- The crate boundaries declared now are the ones later changes fill in, so the dependency graph is fixed early.

**Non-Goals:**
- Any Rust domain code, UI code or FFmpeg binding.
- Making the Windows host a GitHub Actions self-hosted runner.
- Supporting Windows containers or Mono as oracle paths.

## Decisions

### D1. Oracle runs natively on the Windows host over SSH, not in CI and not in Docker
Alternatives: GitHub Actions `windows-latest` (costs minutes, slow feedback, artifacts must be downloaded); Docker with Mono (cannot build the C++/CLI project, partial WinForms); Docker Desktop on the host (Linux backend, cannot run Windows containers without switching modes). The LAN host builds the full solution including FFmpeg bindings, runs the real application when a parity doubt needs manual confirmation, and is reachable with the existing `ssh windows` alias. Scripts are idempotent so the host can be re-provisioned.

### D2. Provision the host with Visual Studio Build Tools 2022 via winget
Components: `Microsoft.VisualStudio.Workload.ManagedDesktopBuildTools`, `Microsoft.Net.Component.4.8.TargetingPack`, `Microsoft.VisualStudio.Workload.VCTools`, `Microsoft.VisualStudio.Component.VC.CLI.Support`. Alternative: full Visual Studio Community (larger, interactive). This is a system change on the user's machine and is executed only after explicit approval, as recorded in tasks.md.

### D3. FixtureGen is a C# console project inside the existing solution
Alternative: scripting the existing `Kinovea.Tests` console. `Kinovea.Tests` is outside the `.sln`, uses commented-out calls as a switch and has no output contract. A dedicated `Kinovea.FixtureGen` project referencing `Kinovea.Services` and `Kinovea.ScreenManager` follows the existing project patterns (old-style csproj, net48, log4net) and gives a stable CLI: `Kinovea.FixtureGen.exe --cases <dir> --out <dir>`. It reuses the fuzzer and synthesizer code by linking the relevant files from `Kinovea.Tests`. No new NuGet dependency is required.

### D4. Fixture contract
Inputs live in `tests/cases/` (hand-written, small, reviewable). Outputs live in `tests/fixtures/<area>/<case>/` with a `manifest.json` recording generator git commit, FFmpeg version and case checksum. Generation is deterministic: fixed random seeds, invariant culture, sorted keys, LF line endings. Floating point values are written with round-trip format (`R`) so Rust can compare with declared tolerances per area.

### D5. Rust workspace layout
Path `rust/` at the repo root, a `Cargo.toml` workspace with these crates, each compiled as a library and holding a placeholder test:

| Crate | Later filled by |
|---|---|
| `kinovea-core` | add-core-types-and-units |
| `kinovea-geometry` | add-geometry-core |
| `kinovea-kinematics` | add-kinematics-filtering |
| `kinovea-measurement` | add-calibration-and-lens-distortion |
| `kinovea-metadata` | add-kva-metadata-model |
| `kinovea-render` | add-headless-renderer |
| `kinovea-video` | add-video-reader-and-cache |
| `kinovea-tracking` | add-tracking |
| `kinovea-export` | add-importers-exporters |
| `kinovea-fixtures` | this change: locate fixtures, load manifests, tolerance helpers |
| `kinovea` (bin) | prints version now; UI shell later |

Toolkit crates (`egui`, `ffmpeg-next`, `opencv`) are not added yet; declaring them without code would only add compile time. Shared settings: `rust-toolchain.toml` pinned to the current stable, `[workspace.lints]` with `clippy::all` as deny, `rustfmt.toml` default, `Cargo.lock` committed.

### D6. CI
New `.github/workflows/rust.yml` on `ubuntu-latest`: checkout, `dtolnay/rust-toolchain` reading `rust-toolchain.toml`, cache via `Swatinem/rust-cache`, then `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`. `build.yml` is not edited; FixtureGen compiles there as part of the solution.

### D7. Quality gates
`testlens.json` language switches to `rust`; `rust/target` is added to all four linter excludes. C# gates lose the `csharp` language because testlens accepts one language; the C# baseline is already recorded and frozen in `.agent/progress.md`.

## Risks / Trade-offs

- [Build Tools installation fails or needs a reboot on the host] → `build.ps1` checks for `MSBuild.exe` via `vswhere` and prints the exact winget command; provisioning is a separate task with manual confirmation.
- [FFmpeg download in `Refs/get-dependencies.ps1` depends on kinovea.org availability] → cache the archive on the host; the script skips the download when the expected folder exists.
- [Fixtures drift when the C# fork changes] → `manifest.json` records the generator commit; a Linux test asserts every fixture manifest points to the same commit, so stale fixtures fail loudly.
- [Non-determinism in C# output (dictionary order, culture, timestamps)] → FixtureGen forces `CultureInfo.InvariantCulture`, fixed seeds and strips timestamps; a repeated run on the host must produce an identical tree, verified by the `fixtures.sh --verify` mode.
- [Host unreachable from outside the LAN] → the `windows-ts` Tailscale alias is accepted as a fallback via `ORACLE_HOST`.

## Migration Plan

1. Land the Rust workspace and CI first (no dependency on the host).
2. Provision the host after approval; verify `build.ps1` compiles the unchanged solution.
3. Add FixtureGen and the first cases; run `fixtures.sh`; commit `tests/fixtures/`.
Rollback: delete `rust/`, `tools/oracle/`, `tests/`, the workflow and the FixtureGen project from the `.sln`. No existing behavior depends on them.
